## Screen changes, Back, feedback and errors in a single-page PWA

**Route changes: focus and title.** A full page load moves focus to the top and has the screen reader announce the new title; a client-side route change does neither unless code does it ([BBC GEL](https://bbc.github.io/gel/foundations/routing), accessed 2026-11-09, confidence: High, tier: Primary). The sources agree that focus must not stay on the clicked link, but they disagree on where it should go. BBC GEL recommends focusing the new screen's `<h1>` (with `tabindex="-1"`), except on first load, and setting `document.title` to "Screen | Application". [Angular's accessibility guide](https://angular.dev/best-practices/a11y) (accessed 2026-11-09, confidence: High, tier: Primary) says to focus "the main content header" and to avoid focus falling back to `body`. [Deque](https://www.deque.com/blog/accessible-routing-in-javascript-frameworks/) (Steadman, 2020; accessed 2026-11-09, confidence: High, tier: Established) ranks the options as the first heading, then the main container with a visible focus ring, then a skip link paired with a live announcement. The one user study, by [Gatsby with Fable Tech Labs](https://www.gatsbyjs.com/blog/2019-07-11-user-testing-accessible-client-routing/) (accessed 2026-11-09, confidence: Medium, tier: Established), had only five participants. Screen reader users there preferred focus on the heading. Magnification users got almost nothing from live-region-only announcements, and focusing a full-width wrapper caused reflow problems when zoomed in. The study ended up recommending focus on a small skip link plus a live region naming the page. Framework defaults also differ. [Next.js](https://nextjs.org/docs/architecture/accessibility) (accessed 2026-11-09, confidence: Medium, tier: Primary) ships an announcer that reads `document.title`, then the `<h1>`, then the path. The Navigation API's `intercept()` defaults to `focusReset: "after-transition"`, which focuses the first `autofocus` element or `<body>` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/NavigateEvent/intercept), accessed 2026-11-09, confidence: Medium, tier: Primary). The [DWP Accessibility Manual](https://accessibility-manual.dwp.gov.uk/guidance-for-your-job-role/software-engineer-or-frontend-developer) (accessed 2026-11-09, confidence: High, tier: Primary) adds that large page updates should update the title and manage browser history, and that titles should take the form "H1 – service", with an "Error:" prefix when the page shows errors. Every source that covers titles agrees that `document.title` should change on every route.

**Back for overlays and viewers.** [Baymard](https://baymard.com/blog/back-button-expectations) (2020; accessed 2026-11-09, confidence: High, tier: Established) found that users expect Back to close an overlay, that mobile users rely on Back more than desktop users because close targets are small, and that 37% of the e-commerce sites it tested got this wrong. Baymard recommends `history.pushState()` when an overlay opens. [NN/g](https://www.nngroup.com/articles/overuse-of-overlays/) (2015; accessed 2026-11-09, confidence: High, tier: Established) says browsers do not treat overlays as pages by default and suggests making Back close the lightbox. Developer forums report that the pushState plus `popstate` pattern can behave differently in installed Android PWAs, and that a viewer closed with its X button must also call `history.back()`, or the leftover entry has to be pressed past later ([Ionic forum](https://forum.ionicframework.com/t/back-button-not-closing-modal-in-ionic-7-angular-17-capacitor-5/247947), accessed 2026-11-09, confidence: Low, **tier: Low**). Chromium's [history-manipulation intervention](https://chromium.googlesource.com/chromium/src/+/127.0.6533.99/docs/history_manipulation_intervention.md) (accessed 2026-11-09, confidence: Medium, tier: Primary) skips history entries that were added without a user activation when the user presses Back, which makes automatic pushes unreliable and limits history traps. Push an entry only from the tap that opens the viewer.

The `CloseWatcher` API is the newer way to handle this. It routes Esc and the Android Back gesture to a component, and `<dialog>` and `popover` respond to Back natively ([Chrome 120 release notes](https://developer.chrome.com/blog/new-in-chrome-120), accessed 2026-11-09, tier: Primary). Watchers created without a user activation are grouped, so one Back press closes them all ([MDN CloseWatcher](https://developer.mozilla.org/en-US/docs/Web/API/CloseWatcher), accessed 2026-11-09, tier: Primary). As of November 2026, [web-features](https://web-platform-dx.github.io/web-features-explorer/features/closewatcher) (accessed 2026-11-09, confidence: High, tier: Primary) lists support in Chrome and Chrome Android 126 and in Firefox and Firefox Android 149 (March 2026), confirmed by [Mozilla bug 1966073](https://bugzilla.mozilla.org/show_bug.cgi?id=1966073). Safari and iOS have no support, so the feature has "Limited availability". The [Navigation API](https://web.dev/blog/baseline-navigation-api) became Baseline Newly Available in early 2026, with Safari 26.2 and Firefox 147 ([web.dev](https://web.dev/blog/baseline-navigation-api), [web-features](https://web-platform-dx.github.io/web-features-explorer/features/navigation), accessed 2026-11-09, confidence: High, tier: Primary). It handles Back/Forward in a single `navigate` handler.

**Toasts, inline messages and banners.** WCAG's [2.2.1 Understanding document](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) (accessed 2026-11-09, confidence: High, tier: Primary) says an auto-dismissing toast is not a time limit if its information is available somewhere else. If it is not, the toast must meet 2.2.1, for example by letting the user extend it with at least 20 seconds' warning. [Roselli](https://adrianroselli.com/2020/01/defining-toast-messages.html) (accessed 2026-11-09, confidence: Medium, **tier: Low**, a recognised expert blog) and [GitHub Primer](https://primer.style/accessibility/toasts/) (accessed 2026-11-09, confidence: High, tier: Primary) both cite 2.2.1, 1.3.2, 2.1.1 and 4.1.3. Primer advises against toasts altogether: it uses no confirmation when the result is visible, banners for complex successes and passive errors, and dialogs for interruptions. [Carbon](https://carbondesignsystem.com/patterns/notification-pattern) (accessed 2026-11-09, confidence: Medium, tier: Primary) keeps inline notifications until the user dismisses them or the problem is resolved, keeps actionable toasts until dismissed, shows one banner at a time, and says not to use timed dismissal for critical messages. Angular Material and Flutter both say snackbars with an action should not auto-dismiss ([Flutter](https://docs.flutter.dev/release/breaking-changes/snackbar-with-action-behavior-update), [Angular Material](https://material.angular.io/components/snack-bar), accessed 2026-11-09, confidence: High, tier: Primary). The [GOV.UK notification banner](https://design-system.service.gov.uk/components/notification-banner/) (accessed 2026-11-09, confidence: Medium, tier: Primary) is limited to one per page, is not used for validation errors, and is removed "when the user moves to a new page". That is the closest source found for clearing stale messages on navigation.

**Plain-language errors and support codes.** [GOV.UK's "problem with the service" pattern](https://design-system.service.gov.uk/patterns/problem-with-the-service-pages/) (accessed 2026-11-09, tier: Primary) bans jargon and codes such as "500" or "bad request", tells users what happened to their data, and gives a way to get help. [NN/g](https://www.nngroup.com/articles/error-message-guidelines/) (2023; accessed 2026-11-09, tier: Established) asks for plain language, specific causes, constructive next steps, preserved input and no blame, and hides codes unless they help diagnosis. [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/alerts) (accessed 2026-11-09, tier: Primary) rejects titles such as "Error 329347 occurred". The plain-language principle is High confidence. [Microsoft's error-message guidelines](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-error) (accessed 2026-11-09, confidence: Medium, tier: Primary) allow a unique, searchable error code shown under "Show details". They always pair it with a text description, and they advise against a generic "contact support" line. Showing a correlation or request ID next to a support instruction, with a copy button, appears only in practitioner write-ups ([SSW Rules](https://www.ssw.com.au/rules-legacy/do-you-return-detailed-error-messages/), accessed 2026-11-09, confidence: Low, **tier: Low**). One of those notes that auto-hiding errors give users no time to copy the ID. No GOV.UK, Material or Apple source covering correlation IDs was found.

**Feedback for every action.** [NN/g's visibility-of-system-status article](https://www.nngroup.com/articles/visibility-system-status/) (Harley, 2018; accessed 2026-11-09, confidence: Medium, tier: Established) calls feedback on user actions a basic guideline. Without it, users repeat actions and lose trust. [Apple HIG Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) (accessed 2026-11-09, tier: Primary) says to confirm completion only for significant actions, because people "only need to know when it doesn't" succeed. Primer agrees that a simple action whose result is visible needs no confirmation.

> Conflicts noted: (1) The focus target after a route change varies: h1 (BBC, Angular, Deque first choice), skip link plus live region (Gatsby study), announcer only (Next.js), body/autofocus (Navigation API default). (2) The CloseWatcher Chrome version varies: Chrome 120 release notes announce it, web-features lists 126. The likely cause is a later behaviour change; this report uses 126 as the baseline. (3) Confirming every action (NN/g) conflicts with confirming only significant ones (Apple, Primer). The two can be reconciled: every action needs visible feedback, which need not be a toast.
> Gaps: No official Material 3 snackbar timing text was retrieved; the page is rendered by JavaScript. No GOV.UK SPA-specific focus guidance was found. No primary-tier source covers user-facing correlation IDs. No source covers a single global `role=alert` banner that persists across routes, apart from the GOV.UK rule to remove banners on a new page. No independent field data was found on how reliable pushState is in installed Android PWAs.

**Implications for Campus Recall (synthesis).** On each hash change, set `document.title` to "Screen – Campus Recall" and move focus to the screen's `<h1>` (`tabindex="-1"`, visible focus ring), except on first load. Open the file viewer with a `history.pushState` entry from the user's tap, close it on `popstate`, and call `history.back()` when the viewer is closed with its X button. `CloseWatcher` can be added as a progressive enhancement for Chrome and Firefox; Safari has no support. Clear the global `role=alert` banner on route change and show errors inline next to their source. Map server and storage strings to plain-language text plus a short copyable reference code, keeping the raw string in logs. Make sure sign out, download and cloud delete each produce visible feedback, for example a changed state, an inline status, or a toast whose content is also visible elsewhere so the 6.5-second dismissal does not cause a 2.2.1 problem.

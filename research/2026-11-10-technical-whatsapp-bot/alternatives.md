## Alternatives to the Official WhatsApp Cloud API, and Their Risks

### 1. Unofficial WhatsApp libraries (Baileys, whatsapp-web.js, WPPConnect, Evolution API)

**How they work.** All four connect to WhatsApp as a *linked device*, the same mechanism as WhatsApp Web, rather than through any Meta-sanctioned business interface. According to the [Baileys README](https://github.com/WhiskeySockets/Baileys) (accessed 2026-11-10, confidence: High, tier: Primary), Baileys is "a WebSockets-based TypeScript library for interacting with the WhatsApp Web API" that authenticates "as a second WhatsApp client by scanning a QR code or Pairing Code with WhatsApp on your phone"; it talks the protocol directly and needs no browser. The [whatsapp-web.js README](https://github.com/wwebjs/whatsapp-web.js) (accessed 2026-11-10, confidence: High, tier: Primary) says it instead uses Puppeteer to run a real WhatsApp Web page in a managed browser instance "to reduce the risk of being blocked". The [Evolution API README](https://github.com/EvolutionAPI/evolution-api) (accessed 2026-11-10, confidence: High, tier: Primary) says Evolution is a REST server that supports two channels: a free "Baileys-based WhatsApp Web API" and Meta's official Cloud API. So Evolution is a wrapper, and its risk depends on which channel is used. WPPConnect is a similar WhatsApp Web wrapper. Because they are linked devices, these tools inherit WhatsApp's linked-device rules. The [WhatsApp Help Center](https://faq.whatsapp.com/378279804439436/?locale=en_US) (accessed 2026-11-10, confidence: Medium, tier: Primary) says a phone can link "up to four devices" and that linked devices "will log out if your phone is unused for over 14 days". This means the bot needs a real phone with its own SIM that someone keeps active.

**Can they receive media and forwarded files?** Yes. The whatsapp-web.js feature table marks "Receive media (images/audio/video/documents)" as supported, and the Baileys README documents `downloadMediaMessage()` on incoming `messages.upsert` events, including a re-upload request for media that has expired on WhatsApp's servers ([Baileys README](https://github.com/WhiskeySockets/Baileys), [whatsapp-web.js README](https://github.com/wwebjs/whatsapp-web.js), accessed 2026-11-10, confidence: High, tier: Primary). A forwarded file reaches a linked device as an ordinary media message, so the technical ingest path works.

**Maintenance status (checked via GitHub API on 2026-11-10).** All four projects are active and none is archived. Baileys (WhiskeySockets, MIT, about 11.6k stars) last pushed code on 2026-11-08. Its latest releases are v6.7.24 and v7.0.0-rc14 (both 2026-07-29), so the 7.x line has been in release-candidate state for a long time and its README warns of "multiple breaking changes". whatsapp-web.js (Apache-2.0, about 22.9k stars) has moved from `pedroslopez/` to the `wwebjs/` organisation; its last release was v1.34.7 on 2026-04-24. WPPConnect (about 3.5k stars) released v2.3.6 on 2026-10-23. Evolution API (about 10k stars) has 2.3.7 (2025-12-05) as its latest stable release and 2.4.0-rc2 (2026-05-17) as its latest release candidate. Sources: the [GitHub repos](https://github.com/WhiskeySockets/Baileys) (accessed 2026-11-10, confidence: High, tier: Primary). Bugs caused by protocol changes appear regularly. For example, Baileys issue [#2488](https://github.com/WhiskeySockets/Baileys/issues/2488) reports an "April 2026 WA protocol regression" that broke pairing-code linking (accessed 2026-11-10, confidence: Medium, tier: Primary). This suggests a team relying on these libraries must budget for unplanned breakage whenever WhatsApp ships a client change.

**WhatsApp Terms of Service position.** The [WhatsApp Terms of Service](https://www.whatsapp.com/legal/terms-of-service) (effective 2021-01-04, accessed 2026-11-10, confidence: High, tier: Primary) forbid using the service in ways that "involve sending illegal or impermissible communications such as bulk messaging, auto-messaging, auto-dialing, and the like". They also forbid users to "reverse engineer, alter, modify, create derivative works from, decompile, or extract code from our Services", to "gain or attempt to gain unauthorized access to our Services or systems", and to "create software or APIs that function substantially the same as our Services", and they bar access "through automated or other means". The [WhatsApp Help Center page on unofficial apps](https://faq.whatsapp.com/1217634902127718) (accessed 2026-11-10, confidence: High, tier: Primary) says that using an unofficial app, or linking your account to one, breaks the Terms. It adds that such accounts can be banned "temporarily or permanently", including losing the ability to link devices. The libraries agree. The whatsapp-web.js README states that "WhatsApp does not allow bots or unofficial clients on their platform, so this shouldn't be considered totally safe". The Baileys README says its maintainers "discourage any stalkerware, bulk or automated messaging usage". WPPConnect's README tells users to "follow applicable terms" (all accessed 2026-11-10, confidence: High, tier: Primary). Two independent primary sources (Meta's Terms and the libraries' own disclaimers) agree that running any of these as a service bot is outside WhatsApp's Terms. **Confidence: High.**

**Documented ban risk, 2025–2026.** There is no published ban rate for each library. The best evidence is a steady stream of first-hand reports in the projects' own issue trackers. These are Primary in the sense of being original user reports, but each one is a single anecdote and unverified (**tier: Low per report, pattern confidence: Medium**). In whatsapp-web.js issue [#3894](https://github.com/wwebjs/whatsapp-web.js/issues/3894) (opened 2025-10-12, 30 comments), many users reported that numbers were "being logged out automatically" and shown a message that "the account is restricted for 24 hours", during which the phone app worked but WhatsApp Web could not be linked; "some accounts have also been banned completely". Issue [#3948](https://github.com/wwebjs/whatsapp-web.js/issues/3948) (2025-11-08) reports that "any phone number I scan" was restricted for 24 hours. In issue [#4008](https://github.com/wwebjs/whatsapp-web.js/issues/4008) (2025-12-08), a user was banned "after 3 messages" despite randomised 20–35 s delays, and a commenter reported a number banned "WITHOUT sending any from my system". In the Baileys tracker, ban reports continue through 2026: [#2309](https://github.com/WhiskeySockets/Baileys/issues/2309) (2026-01-30, a temporary ban twice and then a permanent ban while posting status from a server), [#2441](https://github.com/WhiskeySockets/Baileys/issues/2441) (2026-03-25, a maintainer investigation finding that the undocumented error `463` is a "Reach-out Time-lock" account restriction, possibly a "WEB_COMPANION_ONLY" restriction), [#2707](https://github.com/WhiskeySockets/Baileys/issues/2707) (2026-07-14, "Error 463 … Causing Account Bans"), [#2805](https://github.com/WhiskeySockets/Baileys/issues/2805) (2026-09-07, a verified business account restricted the moment its QR code was scanned), and [#2850](https://github.com/WhiskeySockets/Baileys/issues/2850) (2026-10-07) (all accessed 2026-11-10). Most of these reports involve outbound bulk sending, and a whatsapp-web.js commenter observes that "clients that only reply manually don't have this problem". The October 2025 restriction wave and the cases with no messages sent show that even a receive-mostly bot is not safe. One commenter in #2309 speculates that a server IP far from the phone's location lowers the account's reputation; this is unverified (**confidence: Low**).

**Mass-ban and linked-device enforcement reports.** According to [Intradyn](https://www.intradyn.com/whatsapp-blocked-linked-device-archiving/) (accessed 2026-11-10, confidence: Low, **tier: Low — competing-vendor blog**), from about 2025-09-17 Meta flagged the TeleMessage WhatsApp archiver as an "unofficial app" and blocked the affected WhatsApp accounts "from creating *any* linked device sessions at all". Meta lifted the restriction on 2026-02-04. If accurate, this shows that the penalty for an unofficial companion can land on the *personal account*, not only on the bot session. Its timing matches the October 2025 whatsapp-web.js restriction wave above. I found no independent Established-tier article confirming either event as a deliberate mass action, so it is presented as a pattern, not a fact. For scale, Indian media summarising WhatsApp's statutory [India monthly compliance reports](https://www.whatsapp.com/legal/india-monthly-reports) (accessed 2026-11-10, tier: Primary) report about 9.7–9.9 million Indian accounts banned per month in early 2025. [Business Today](https://businesstoday.in/technology/news/story/whatsapp-banned-97-million-indian-accounts-in-february-heres-why-470175-2025-04-01) gives 9.7 million for February 2025 with more than 1.4 million banned proactively, and [Inc42](https://inc42.com/buzz/whatsapp-banned-99-6-lakh-accounts-in-january-2025/) gives about 99.67 lakh for January 2025 (accessed 2026-11-10, confidence: High, tier: Established). These totals are not broken down by cause, so they show how aggressive automated enforcement is, not how many bans come from these libraries.

**Meta legal actions.** I found no 2025–2026 lawsuit by Meta against the authors or ordinary users of Baileys, whatsapp-web.js, WPPConnect or Evolution API. Three relevant precedents exist. First, WhatsApp announced in 2019 that from 7 December 2019 it would "take legal action against those we determine are engaged in or assisting others in abuse" of automated or bulk messaging, even on off-platform evidence alone ([SecurityWeek](https://www.securityweek.com/whatsapp-will-take-legal-action-against-automated-or-bulk-messaging), [The Quint](https://www.thequint.com/tech-and-auto/tech-news/whatsapp-legal-action-against-abusers), accessed 2026-11-10, confidence: High, tier: Established). Second, in 2022 Meta sued Rockey Tech HK and others over "unofficial" WhatsApp apps alleged to have compromised over a million accounts, for breach of the Terms and developer agreements ([Gizmodo](https://gizmodo.com/whatsapp-facebook-fake-app-takeovers-meta-sues-1849631883), [Docket Alarm, N.D. Cal. 4:22-cv-05711](https://www.docketalarm.com/cases/California_Northern_District_Court/4--22-cv-05711/WhatsApp_LLC_et_al_v._Rockey_Tech_HK_Ltd._et_al/1/), accessed 2026-11-10, confidence: High, tier: Established/Primary). Third, in WhatsApp v. NSO Group a jury awarded about US$167.7 million in May 2025 under the US federal and California anti-hacking laws (CFAA/CDAFA). On 2025-10-17 the judge cut punitive damages to about US$4 million but granted a permanent injunction barring NSO from targeting WhatsApp ([Engadget](https://www.engadget.com/cybersecurity/court-reduces-damages-meta-will-get-from-spyware-maker-nso-group-but-bans-it-from-whatsapp-163016648.html), [The Record](https://therecord.media/judge-bars-nso-from-targeting-whatsapp-users-lowers-damages), [Davis Polk](https://www.davispolk.com/experience/trial-victory-meta-and-whatsapp-spyware-case), accessed 2026-11-10, confidence: High, tier: Established). This suggests Meta is willing to litigate unauthorised access to WhatsApp's servers, but its actual targets so far are malware and spyware operators and commercial abusers. A student pilot is far more likely to lose a number than to be sued (analysis, **confidence: Low**).

**Extra finding: supply-chain risk.** According to [The Hacker News](https://thehackernews.com/2025/12/fake-whatsapp-api-package-on-npm-steals.html), [SecurityWeek](https://www.securityweek.com/npm-package-with-56000-downloads-steals-whatsapp-credentials-data/) and [The Register](https://www.theregister.com/2025/12/22/whatsapp_npm_package_message_steal/) (accessed 2026-11-10, confidence: High, tier: Established), the npm package `lotusbail` was a working fork of Baileys with over 56,000 downloads. It stole messages, contacts, media and session credentials, and it used a hardcoded pairing code to link the attacker's own device. That device stayed linked even after the package was uninstalled. The Baileys ecosystem is crowded with similarly named forks (for example `@chatunity/baileys`), so a team adopting it must pin the exact upstream package.

**Extra finding: the "Message yourself" trap.** Because these libraries act as linked devices, one tempting design is to have each student link *their own* WhatsApp account to the Campus Recall server, so the server can read the student's "Message yourself" chat directly. This is analysis, not a sourced recommendation. That design would give a student-run server read access to every chat on every participant's personal account. It would put participants' personal numbers at risk of the restrictions documented above, possibly including losing linked-device access ([Intradyn](https://www.intradyn.com/whatsapp-blocked-linked-device-archiving/), Low tier). It would also clearly fall under the Terms' ban on linking accounts to unofficial apps ([WhatsApp Help Center](https://faq.whatsapp.com/1217634902127718)). It should be ruled out on privacy and ethics grounds alone.

### 2. Third-party "WhatsApp to X" automation services

The mainstream no-code platforms all use Meta's official Cloud API for WhatsApp. According to [Zapier's help centre](https://help.zapier.com/hc/en-us/articles/40123068069005/) and its [WhatsApp Business app pages](https://zapier.com/apps/notion/integrations/whatsapp-business/255704936/create-new-notion-pages-from-new-whatsapp-business-messages-received) (accessed 2026-11-10, confidence: Medium, tier: Primary), Zapier's "WhatsApp Business" app authenticates by logging into a "WhatsApp Business Cloud account", and its "New Message Received" trigger fires only for messages to a registered business number. [Make's WhatsApp Business Cloud app](https://www.make.com/en/help/app/whatsapp-business-cloud) (accessed 2026-11-10, confidence: Medium, tier: Primary) offers a "Watch Events" webhook module and links to Meta's pricing documentation. [n8n's WhatsApp Trigger docs](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.whatsapptrigger/) (accessed 2026-11-10, confidence: Medium, tier: Primary) say n8n registers its webhook on your Meta app, and that the app must also be subscribed to your WhatsApp Business Account (WABA), or messages "never reach n8n". The n8n template [#4213](https://n8n.io/workflows/4213) shows the media path: take the media ID from the webhook, fetch a private media URL, then download it with an authenticated request (accessed 2026-11-10, confidence: Medium, tier: Primary). Because Zapier, Make and n8n are all Cloud API clients, they add a paid automation layer but none of the friction or approval steps go away. Community threads on [Make](https://community.make.com/t/whatsapp-watch-events-trigger-verification-succeeds-but-no-inbound-messages-received/76751) and [Zapier](https://community.zapier.com/troubleshooting-99/whatsapp-business-trigger-not-firing-despite-successful-connection-in-zapier-53470) report webhooks that verify but never receive messages (**tier: Low**).

A second group of "WhatsApp to Notion/Sheets" connectors sits on intermediary gateways, and several of those gateways are unofficial. Zapier and Pipedream list integrations with 2Chat, TimelinesAI, UltraMsg, Green-API, Wassenger and WATI ([Pipedream UltraMsg–Notion](https://pipedream.com/apps/ultramsg/integrations/notion), [Zapier TimelinesAI–Notion](https://zapier.com/apps/notion/integrations/timelinesai/1820259/create-new-notion-database-items-from-new-received-messages-in-timelinesai), accessed 2026-11-10, tier: Primary for the existence of the listings). [Green-API's own article](https://green-api.com/articles/en/unofficial-whatsapp-api-what-is-it-and-how-to-use-it/) describes itself as an "unofficial WhatsApp API": an HTTP gateway that connects a normal account "as a linked device … usually with a QR code". [2Chat's developer page](https://2chat.co/developers) says it runs the QR-based connection for customers and also offers official WABA numbers (accessed 2026-11-10, confidence: Medium, tier: Primary — vendor self-description). WATI is an official Business Solution Provider (BSP). These gateways therefore carry the same Terms and ban risk as Section 1, plus a third party holding the session. I found no product actually named "SaveToNotion" or "Notion WhatsApp" that captures forwarded WhatsApp messages; **No sources found for** a dedicated, well-known consumer "forward to WhatsApp, save to Notion" bot. The IFTTT applets found use an "InOut" WhatsApp bot of unclear provenance ([IFTTT](https://ifttt.com/applets/xwaCK8yh-create-a-notion-page-when-a-whatsapp-message-is-received), accessed 2026-11-10, **tier: Low**). Readwise, a close analogue to Campus Recall, offers capture through email, a Discord bot and share extensions, but I found no WhatsApp channel ([Readwise changelog](https://readwise.io/changelog), accessed 2026-11-10, confidence: Medium, tier: Primary).

### 3. Telegram Bot API as an alternative channel

**Cost and limits.** According to the [Telegram Bots FAQ](https://core.telegram.org/bots/faq) (accessed 2026-11-10, confidence: High, tier: Primary), "bots are able to message their users at no cost". The rate limits are about one message per second per chat and about 30 messages per second for broadcasts; paid broadcasts in Telegram Stars apply only above that and only for bots with 100,000 or more monthly active users. The [Telegram Bot API reference](https://core.telegram.org/bots/api) (Bot API 10.4, 2026-11-09, accessed 2026-11-10, confidence: High, tier: Primary) states for `getFile` that "the maximum file size to download is 20 MB", and download links are valid "for at least 1 hour". Bots can upload files of "up to 50 MB" (10 MB for photos). A self-hosted [Local Bot API server](https://github.com/tdlib/telegram-bot-api) lets a bot "download files without a size limit" and "upload files up to 2000 MB". The 20 MB download cap would block many lecture-slide PDFs and scanned notes on the hosted API. A small local Bot API server container on the team's Azure VM removes the cap (analysis).

**Inline buttons and deep-link login.** The [Telegram bot features page](https://core.telegram.org/bots/features) (accessed 2026-11-10, confidence: High, tier: Primary) documents inline keyboards "shown directly below their relevant messages", whose presses send callbacks rather than chat messages. This suits a "Saved ✓ — [Open] [Add tag] [Undo]" reply. Deep links `https://t.me/<bot>?start=<param>` accept a parameter of up to 64 characters drawn from `A-Z a-z 0-9 _ -`. The page explicitly names the use case of passing "an authentication token to connect the user's Telegram account to their account on another platform". So linking a Campus Recall account to Telegram is a one-tap, officially supported flow, with no Meta Business verification, phone number, templates or app review.

**Popularity in India.** WhatsApp is dominant. [Reuters](https://tech.yahoo.com/apps/articles/whatsapp-adds-rival-app-payment-054726341.html) and [TechCrunch](https://techcrunch.com/2024/07/31/india-is-the-largest-market-for-meta-ai-usage) both put WhatsApp at "more than 500 million users" in India, its largest market (accessed 2026-11-10, confidence: High, tier: Established). Among India's mainly English-speaking online sample, the [Reuters Institute Digital News Report 2025](https://reutersinstitute.politics.ox.ac.uk/digital-news-report/2025/india) (accessed 2026-11-10, confidence: Medium, tier: Established) reports WhatsApp used for news by 46%. It does not list Telegram. Several sources call India Telegram's largest market, but reputable figures are scarce. [Cointelegraph](https://cointelegraph.com/news/telegram-under-investigation-india-report) (2024) cites "an estimated 104 million users" (accessed 2026-11-10, confidence: Low, tier: Established-crypto trade press, figure traced to Statista). Aggregators such as [DemandSage](https://www.demandsage.com/telegram-statistics/) give 150 million or more (accessed 2026-11-10, confidence: Low, **tier: Low**). Globally, Telegram passed 1 billion monthly active users in March 2025 per [Backlinko](https://backlinko.com/telegram-users) relaying Durov's announcement (accessed 2026-11-10, confidence: Low, **tier: Low**). For Indian college students specifically, **No sources found for** a current (2025–2026) representative survey of Telegram versus WhatsApp use. A 2024 study of 150 respondents found students had a "favourable perception" of WhatsApp and a "neutral perception" of Telegram for learning ([NCERT IJET](https://journals.ncert.gov.in/IJET/article/view/284), accessed 2026-11-10, confidence: Low, tier: Primary but small sample). Anecdotally, Indian students widely use Telegram channels for sharing study material and PDFs; this is my inference and unsourced. Telegram is installed on many student phones, but it is not the default "send to self" habit that WhatsApp is.

### 4. Non-chat friction reducers

**Web Share Target API.** [MDN browser-compat-data](https://github.com/mdn/browser-compat-data/blob/main/manifests/webapp/share_target.json) (accessed 2026-11-10, confidence: High, tier: Primary) lists the manifest `share_target` member as supported in Chrome Android 76+, desktop Chrome 89+, Edge, Opera and Samsung Internet. It lists it as *not* supported in Safari, Safari iOS, iOS WebView, Firefox or Android WebView. [WebKit bug 194593, "Add support for Web Share Target API"](https://bugs.webkit.org/show_bug.cgi?id=194593) (accessed 2026-11-10, confidence: High, tier: Primary), filed 2019-02-13, was still in status NEW at its last activity on 2026-05-23. A commenter there notes that WebKit's standards position has been "neutral since 2023". Two primary sources agree: on Android, an *installed* Campus Recall PWA can appear in the system share sheet, so "Share → Campus Recall" from WhatsApp, Files or Gallery works. On iOS it cannot as of November 2026. This still requires installing the PWA, which is the friction reviewers objected to, but on Android installing is a single "Add to Home screen" step.

**iOS Shortcuts share-sheet to a web endpoint.** According to Apple's [Shortcuts User Guide](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios) (accessed 2026-11-10, confidence: Medium, tier: Primary), the "Get Contents of URL" action supports POST/PUT/PATCH with a Request Body of "JSON, a Form, or a File". Apple's [input-types page](https://support.apple.com/guide/shortcuts/apd7644168e1/ios) (accessed 2026-11-10, confidence: Medium, tier: Primary) says a shortcut with "Show in Share Sheet" enabled receives the shared item as input; the "Files" type covers documents, images and PDFs. It also warns that share-sheet shortcuts "have limited RAM" and may quit on large data. A shareable iCloud shortcut that POSTs the shared file with a per-user token to the Campus Recall backend is therefore a workable iOS stand-in for Web Share Target. It requires each student to add the shortcut once, and large PDFs may fail (analysis).

**Email-in.** [Readwise Reader](https://docs.readwise.io/reader/docs/faqs/email-newsletters) gives each user hard-to-guess "Library" and "Feed" email addresses ("you don't need to whitelist any sending addresses"). Per [Readwise help](https://help.readwise.io/article/159-how-do-i-whitelist-a-new-email-address-so-i-can-send-documents-to-my-readwise-account), emailed PDFs and attachments are imported (accessed 2026-11-10, confidence: High, tier: Primary). [Evernote's help centre](https://help.evernote.com/hc/articles/209005347) (accessed 2026-11-10, confidence: Medium, tier: Primary) documents an "Email Notes to" address with a limit of 200 emails per day. [Labnol](https://labnol.org/internet/evernote-email-notes/28961) reports that Evernote dropped email-to-note for free accounts (accessed 2026-11-10, confidence: Low, **tier: Low**). Because every student has an IITGN email account, and both phone platforms have "share to Mail", a per-user `save+<token>@…` address is a channel needing no installation and no ToS risk. On Azure it needs an inbound mail provider, such as a SendGrid/Mailgun inbound-parse webhook or a catch-all mailbox; I did not research this in detail (analysis).

**WhatsApp "Message Yourself" behaviour.** WhatsApp announced Message Yourself on 2022-11-28 as a one-to-one chat with yourself for "notes, reminders and shopping lists", which can be pinned and syncs across linked devices ([TechCrunch](https://techcrunch.com/2022/11/28/whatsapp-rolls-out-a-feature-that-makes-it-easier-to-message-yourself/), [Engadget](https://www.engadget.com/whatsapp-now-lets-you-send-messages-to-yourself-124010198.html), accessed 2026-11-10, confidence: High, tier: Established). Self-chat messages are end-to-end encrypted and exist only on the user's own devices, so no official API exposes them. A Cloud API bot only sees messages sent *to the bot's business number* (cross-reference: Cloud API axis). This implies the "send to save" habit transfers only if the student pins the bot's chat next to, or instead of, their self-chat. Forwarding to a pinned bot takes the same number of taps as forwarding to self (analysis).

### 5. Verdict per option (analysis, for a three-student IITGN pilot)

| Option | ToS / ban risk | Cost | Friction for student | Verdict |
| --- | --- | --- | --- | --- |
| Baileys / whatsapp-web.js / WPPConnect / Evolution (Baileys mode) on a dedicated SIM | **High.** Explicitly against WhatsApp's Terms; 2025–2026 restriction waves documented; number loss likely over a semester | Free software, plus a SIM and a phone kept online every 14 days | Lowest: just a contact to forward to | Acceptable only as a throwaway prototype on a burner number. Not for a pilot that reviewers or the institute will see. Never link students' personal accounts. |
| Unofficial gateways (Green-API, UltraMsg, 2Chat QR mode) | **High.** Same mechanism, plus a third party holding the session and the data | Subscription | Lowest | Reject: same risk as self-hosting, with an added privacy exposure. |
| Zapier / Make / n8n on Cloud API | **Low.** Official route | Automation-plan cost on top of Cloud API setup | Same as Cloud API | Adds cost and a dependency without removing Meta onboarding. Calling the Cloud API directly from Node is simpler. |
| Telegram bot (+ local Bot API server) | **None.** Bots are first-class | Free | Low if the student already has Telegram; otherwise an install | Strongest zero-risk chat channel. Build first or in parallel as a fallback. |
| Web Share Target (installed PWA) | None | Free | Android: low after install. iOS: not available | Cheap to add now. Covers Android users without any bot. |
| iOS Shortcut to an upload endpoint | None | Free | One-time shortcut install | Good iOS complement to Share Target. |
| Email-in (`save+token@…`) | None | Low (inbound-parse service) | None: works from any mail app | Best universal no-install fallback, especially for PDFs. |

Overall, the evidence suggests a combination of the official WhatsApp Cloud API (covered in another axis) or a Telegram bot, plus Web Share Target, an iOS Shortcut and email-in. This covers almost all students with no ban exposure. Unofficial WhatsApp libraries trade a small gain in friction for a high, well-documented chance of losing the bot's number in mid-pilot.

> **Conflicts noted:**
> - **Who gets banned in the 2025–2026 waves.** Users in whatsapp-web.js [#4008](https://github.com/wwebjs/whatsapp-web.js/issues/4008) say bans hit only heavy senders ("clients that only reply manually don't have this problem"). Others in the same thread report bans with no messages sent. The sources disagree, and both are single anecdotes, so I treat a receive-only bot as lower risk but not safe.
> - **India WhatsApp user count.** Figures range from "more than 500 million" (Reuters, TechCrunch) to 535.8 million or 853.8 million (aggregators). I use the conservative Reuters/TechCrunch ">500 million".
> - **India Telegram user count.** Figures range from 86.6 million (2022) to 104 million (Statista via Cointelegraph, 2024) to 150–200 million (Low-tier aggregators). None comes from Telegram itself, so all are Low confidence.
>
> **Gaps:**
> - No sources found for a per-library ban *rate*.
> - No Established-tier confirmation of a deliberate 2025 "mass ban" of unofficial linked-device clients; the evidence is issue trackers plus one vendor blog.
> - No sources found for any 2025–2026 Meta lawsuit against Baileys or whatsapp-web.js maintainers or users.
> - No current survey of WhatsApp versus Telegram use among Indian college students.
> - No product named "SaveToNotion" or "Notion WhatsApp" that captures forwarded WhatsApp messages was found.
> - Evernote's current email-in plan restrictions were not verified on a primary page.
> - Inbound-email providers and their cost on Azure were not researched.

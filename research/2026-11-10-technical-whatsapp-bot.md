# Research Report — WhatsApp bot as a save-and-search channel for Campus Recall

> **Type:** technical | **Date:** 2026-11-10 | **Constraints:** India (IITGN students), student team, hosted Azure pilot ends 6 December 2026
>
> **Goals:** Is a WhatsApp bot that saves messages/files into the Azure vault and answers searches possible? What does it cost, what do Meta's rules allow, what breaks in our privacy promises, and how would we build it on the existing pilot?

> **Assumptions:** The bot builds on the existing optional Auto-sync pilot (`pilot/`: Node API, PostgreSQL, private Azure Blob, IITGN Google sign-in, owner key `google:<sub>`). ## Bottom line

**Yes, it is possible, and the official route is open to a three-person student team at no cost for a demo.** One correction to the premise: the bot cannot read a student's "Message yourself" chat. That chat is end-to-end encrypted and lives only on the student's own devices, and a Cloud API bot sees only messages sent to its own business number (analysis in the alternatives note; feature facts from [TechCrunch](https://techcrunch.com/2022/11/28/whatsapp-rolls-out-a-feature-that-makes-it-easier-to-message-yourself/); High, Established). The habit transfers instead: the student pins a "Campus Recall" contact and forwards to it, which takes the same taps as forwarding to themselves.

**How it works.** Meta's WhatsApp Cloud API calls a webhook on our existing pilot server, which copies each file into the Azure vault through the pilot's existing upload path, and the app sees it through the existing change feed. The server then indexes the item with the app's own engine running in headless Chromium (decided 10 November), so WhatsApp items are searchable by meaning straight away, in the chat and in the app. To search from WhatsApp, the same engine embeds the question, ranks the student's stored index bundles, and the bot replies with a short list and re-sends the original the student taps. Unofficial libraries such as Baileys break WhatsApp's Terms and were still drawing bans in October 2026, so they are ruled out.

**The main trade-off is privacy, and the bot is opt-in for that reason.** For students who link the bot, the app's local-first promise no longer holds: Meta decrypts every message and keeps it for up to 30 days, our server processes their files and sees every query, and WhatsApp labels the chat as not end-to-end encrypted ([Meta Cloud API privacy](https://developers.facebook.com/documentation/business-messaging/whatsapp/data-privacy-and-security); High, Primary). Students who never link it keep the app exactly as today. Meta also charges for replies beyond 1,000 a month and decides in its "sole discretion" which bots count as banned AI providers, so the bot is a capture-and-search channel on top of the vault, never the system of record. The demo stays free (test number, five phones, existing VM) and targets about 24 November: saving first, then server indexing, then search in WhatsApp.

## Starting point in our codebase

The repository already contains most of the server half a WhatsApp bot would need. According to `docs/pilot/protocol.md`, the optional Auto-sync pilot runs a plain `node:http` API (`pilot/server/`) with PostgreSQL 17 and a private Azure Blob container, verifies IITGN Google sign-in itself, and keys every vault by `google:<sub>`. Uploads go through begin/chunk/complete with SHA-256 and length checks, per-kind limits (20 MB images and PDFs, 50 MB audio, 100 MB video, 20,000 code points of text), a 200 MB account quota, idempotent `opId`s, a change feed, rate limiting and nightly logical backups. A server-side ingester could therefore publish a WhatsApp file as an ordinary cloud item through the same store, and every signed-in device would see it through the existing change feed.

The gap is search. The server never runs a model: OCR, transcription and the 768-dimensional embeddings are produced in the browser, and a device publishes an index bundle only for items it processed itself (`PUT /items/{id}/index`). An item that arrives from WhatsApp would sit in the vault with search state `pending`, and no device would currently pick it up. Two promises also matter. Pilot statement P06 says "No query text leaves the device" (`docs/pilot/SPEC.md`), and the root SPEC says no external AI API, hosted embeddings or cloud inference are used. A bot that answers searches inside WhatsApp necessarily sends query text to Meta and to our server, so it cannot sit under P06 as written; it needs its own opt-in statement.

The pinned models matter for any server-side search. `src/engine/model.worker.ts` loads `onnx-community/embeddinggemma-2-ONNX` at revision `daa72c5` (q4) through Transformers.js for text, image and query vectors, and `onnx-community/whisper-tiny.en` for speech; `INDEX_VERSION` is `gemma2-daa72c5-q4-768-ch256o48-img70-lowered1-notitledup1-asr2-ocrconf1-v8`. A server that embeds WhatsApp queries must run the same model, revision and query formatting, or its vectors will not be comparable with the device-made bundles.

**Team decisions (scope interview, 10 November):** devices index WhatsApp items later (no server OCR/image/speech models); students can also search from inside WhatsApp; a WhatsApp number alone identifies a library (no IITGN Google sign-in required); the target is a demo before 6 December 2026. These choices interact. With no Google account, the app needs another way into a WhatsApp-created vault (a one-time link sent by the bot), and WhatsApp search needs at least the query encoder, or keyword matching, on the server.

**Follow-up decisions (10 November, later):** the WhatsApp bot is strictly opt-in; a student who never links it keeps the app's existing local-only and "no query text leaves the device" promises unchanged. The demo must cost nothing and be ready within about two weeks (around 24 November); pricing beyond the demo is deferred. Both fit the plan: Meta's test number needs no payment method, a five-phone demo stays far below 1,000 free replies a month, and the existing pilot VM is reused. The team is reconsidering where WhatsApp items are indexed. Today the pilot server is only a storage and sync relay (sign-in, originals, device-made index bundles, change feed, backups) and runs no models, which is why a photo sent by WhatsApp has no meaning index until a device processes it. Because the bot is opt-in anyway, the server could index opted-in items itself. The lowest-risk way is to run the app's own built engine in headless Chromium on the VM through Playwright, as the repository's actual-model tests already do, so the server produces bundles with the same code, models and `INDEX_VERSION` as the devices instead of a Node port of `src/engine/extract.ts`, which uses DOM canvas, `createImageBitmap` and workers.

The hosted pilot also has a fixed end: the README states it runs until 6 December 2026, 17:47 IST, about 26 days from today. Any WhatsApp work either fits inside that window or needs the pilot extended.

## Technology Landscape

### Getting a number and receiving messages (Cloud API mechanics)

Meta's onboarding asks little of a student team. Personal Facebook accounts, a developer app with the WhatsApp use case and a self-created business portfolio are enough; business verification is not a step, and the flow registers a test number automatically ([Meta Get Started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started.md); Medium, Primary). Test resources need no payment method ([Meta About the platform](https://developers.facebook.com/documentation/business-messaging/whatsapp/about-the-platform); Medium, Primary). The test number reaches about five allow-listed recipients, but that cap appears on Meta's [legacy Get Started page](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started/) and in vendor help, not on the current page (Low–Medium). A real number cannot already be on WhatsApp ([Meta phone numbers](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers); High, Primary), so the practical route is a new prepaid SIM; coexistence with a WhatsApp Business app number requires Tech Provider status (Medium, Primary). Staying unverified is workable, because the 250 limit counts only users messaged *outside* a customer service window ([Meta Messaging Limits](https://developers.facebook.com/docs/whatsapp/messaging-limits); High, Primary) and students always message first. The cost is cosmetic: the display name is reviewed only at the 2,000 tier, so students will probably see a raw number ([Meta Display Names](https://developers.facebook.com/documentation/business-messaging/whatsapp/display-names); Medium, Primary).

Inbound webhooks give the ingester what it needs. Image, video and document messages carry `id`, `mime_type`, `sha256` and `caption` (documents add `filename`); voice notes arrive as OGG/Opus with `voice: true` and no caption ([Meta webhook reference](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/components); Medium, Primary). Download URLs expire after five minutes and webhook media IDs after seven days, cut from 30 days in October 2025 ([Meta media reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media), [changelog](https://developers.facebook.com/documentation/business-messaging/whatsapp/changelog/); High, Primary). Size caps are 5 MB for images, 16 MB for audio and video and 100 MB for documents, and a larger inbound file arrives as error 131052 instead of a file (Medium, Primary). The inbound `url` field is dated 16 October 2025 in the changelog but "starting November 12, 2025" on the reference pages, so code should fall back to `GET /<media-id>`. `context.forwarded` is undocumented for documents and voice notes, and community reports say albums arrive as one webhook per item (Low).

Delivery is at-least-once. Non-200 responses are retried "over the next 7 days" and "can result in duplicate webhook notifications"; payloads are signed with `X-Hub-Signature-256` over the raw body and must reach a CA-signed endpoint ([Meta webhook endpoint](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/create-webhook-endpoint); High, Primary). Meta's generic Graph guide says 36 hours and a community post 8 hours; 7 days is the conservative design figure. Free-form replies are allowed only inside the 24-hour window each user message opens, otherwise error 131047 ([Meta pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing); High, Primary). Lists hold 10 rows with 24-character titles, reply buttons three, and CTA messages one URL ([Meta list messages](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-list-messages); High, Primary); an unpublished per-recipient rate limit (131056) is a reason to batch acknowledgements (Medium). Since April 2026 webhooks carry a business-scoped user ID, a user with a username may arrive without a phone number, and Meta says to "build your integration to identify users by BSUID" ([Meta BSUIDs](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids); High, Primary). The On-Premises client expired on 23 October 2025, so older tutorials built on it are obsolete (High, Primary). Full detail: `research/2026-11-10-technical-whatsapp-bot/cloud-api-mechanics.md`.

### Cost

Free replies ended recently. According to [Meta's pricing page](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing) (High, Primary; corroborated by [Beebom](https://gadgets.beebom.com/news/whatsapp-stopping-messages-from-select-business-accounts-starting-october-2026); High, Established), Meta resumed charging for service replies on 1 October 2026. Each business number gets 1,000 free service messages a month, without rollover, and India then pays ₹0.115 per reply, about ₹0.136 with 18% GST. In-window utility templates are charged from the first message, so the bot should reply with free-form messages. Messages from users are never charged, and no source describes a charge for downloading media (Medium, Primary). Beyond the free tier a payment method is mandatory: without one, Meta delivers service messages "within the free tier but not ... after the free tier has been used" (High, Primary). Indian accounts must bill in INR by 31 December 2026, so the team should pick INR at creation (Medium, Primary). The next possible rate change is 1 January 2027 (High, Primary).

The pricing note's own estimate, assuming one free-form reply per inbound message and no templates, is below. Two replies per upload roughly doubles each row.

| Scenario | Replies/month | Meta direct (incl. GST) | Twilio (excl. tax) |
| --- | --- | --- | --- |
| 20 students × 5 items/week | ~433 | ₹0 | ~$4.33 |
| 100 students × 15/week | ~6,500 | ~₹746 | ~$72.70 |
| 500 students × 30/week | ~65,000 | ~₹8,685 | ~$739.60 |

Intermediaries add cost without saving work. Twilio charges $0.005 on every inbound and outbound message, about eight times Meta's India service rate, and its sandbox needs a `join` code per user and expires after three days ([Twilio pricing](https://www.twilio.com/en-us/whatsapp/pricing), [sandbox docs](https://www.twilio.com/docs/whatsapp/sandbox); Medium, Primary). India-focused providers put inbound webhooks in plans of about ₹2,800 to ₹5,800 a month ([Interakt](https://www.interakt.shop/pricing), [WATI](https://www.wati.io/pricing/); Medium, Primary). Telegram bots message users "at no cost" ([Telegram Bots FAQ](https://core.telegram.org/bots/faq); High, Primary).

The Azure side matters as much. The pilot's D2as_v4 costs about $66 a month in India South Central ([Azure Retail Prices API](https://prices.azure.com/api/retail/prices); Low by the two-source rule, though Primary), and Azure for Students gives $100 of credit for 12 months ([Microsoft](https://azure.microsoft.com/pricing/offers/ms-azr-0170p/); High, Primary). The current VM alone would use that credit in about six weeks (analysis), so a design that needs a bigger VM doubles the burn. Full detail: `research/2026-11-10-technical-whatsapp-bot/pricing.md`.

### Policy and privacy

Meta's AI-provider clause is the main policy risk. Section 4.7 of the [Meta Terms for WhatsApp Business Platform](https://www.facebook.com/legal/Meta-Terms-for-WhatsApp-Business-Platform) (modified 23 September 2026; Medium, Primary) bars providers of "artificial intelligence or machine learning technologies", "as determined by Meta in its sole discretion", when that technology is "the primary (rather than incidental or ancillary) functionality", and bars training models on WhatsApp Platform Data. The EU, Italy and Brazil forced Meta to reopen access ([Commission IP/26/1276](https://ec.europa.eu/commission/presscorner/api/files/document/print/en/ip_26_1276/IP_26_1276_EN.pdf), [AGCM A576](https://en.agcm.it/en/media/press-releases/2025/12/A576); High, Primary; [TechCrunch on CADE](https://techcrunch.com/2026/03/06/after-europe-whatsapp-will-let-rival-ai-companies-offer-chatbots-in-brazil/); High, Established), but India (+91) is not on Meta's list of permitted markets ([Meta AI Providers page](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/ai-providers); Medium, Primary), and no Competition Commission of India action was found. On our reading, a bot that stores a student's own files and returns them uses ML only to rank, which is "ancillary" (analysis, Low–Medium). Meta decides, though, and the clause names "machine learning" broadly. Describing the bot as a file locker, answering only with saved items and never generating answers or training on WhatsApp content all strengthen that reading.

The [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/) (updated 23 September 2026; Medium, Primary) requires opt-in, honouring opt-outs, a published privacy policy and "prompt, clear, and direct escalation paths" to a human. It forbids asking for card, account or ID numbers, so the bot should warn students not to send ID cards and fee receipts, and it forbids passing one customer's data to another, which constrains any future sharing feature. Storing users' files on our own servers is expected: Meta "does not provide an archiving service" (Terms, Section 5.4). A vendor blog claims AI disclosure became mandatory in January 2026, but the primary policy text has no such rule, so disclosure is treated as good practice.

Encryption ends at Meta. Cloud API "decrypts the message and forwards it to the business", acts as a processor and keeps messages for at most 30 days ([Meta Cloud API privacy](https://developers.facebook.com/documentation/business-messaging/whatsapp/data-privacy-and-security); High, Primary), and WhatsApp shows such chats as not end-to-end encrypted ([WhatsApp Help Center](https://faq.whatsapp.com/general/28030015/?locale=en_US); High, Primary). A search snippet once quoted the privacy page as saying "WhatsApp cannot access any message content"; the fetched page does not, and this report follows the fetched page. Meta's Local Storage option, which keeps data at rest in India after up to 60 minutes of processing elsewhere, and a "No Storage" mode could narrow the exposure, but neither was tested ([Meta Local Storage](https://developers.facebook.com/documentation/business-messaging/whatsapp/local-storage); Medium, Primary).

India's DPDP duties are close. The [DPDP Rules 2025](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf) were notified on 14 November 2025, and the notice, security, breach, children's-data and rights duties start around 13 May 2027 (High, Primary; commentators give 12–14 May). They require an itemised notice, withdrawal as easy as consent, breach notice to students and a report to the Board within 72 hours, grievance replies within 90 days, and verifiable parental consent for anyone under 18, which may include some first-year students; penalties reach ₹250 crore ([PIB explainer](https://static.pib.gov.in/WriteReadData/specificdocs/documents/2025/nov/doc20251117695301.pdf); High, Primary). A team running a service for other students is very likely a Data Fiduciary (analysis, not legal advice), so the consent notice, delete-all command, grievance contact, breach plan and 18+ confirmation belong in the first build. No IITGN policy on student apps was found; the one candidate ISTF PDF returned 404. Full detail: `research/2026-11-10-technical-whatsapp-bot/policy-privacy.md`.

### Server-side search architecture

Vector parity is a hard constraint. Any server vector, including a bot query, must come from the same pinned `embeddinggemma-2-ONNX` q4 files and query formatting as the devices. The [model card](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX) (Medium, Primary) puts q4-to-fp32 text cosine at 0.988, so a q8 server against q4 devices could move results across the frozen thresholds. Transformers.js in Node runs on `onnxruntime-node` ([transformers.js source](https://app.unpkg.com/@huggingface/transformers@4.2.0/files/src/backends/onnx.js); Medium, Primary), so the browser's preprocessing and query formatting can be reused unchanged; whether the WASM-only q4 Gather patch (`src/engine/onnx-q4.ts`) is needed natively must be tested. Bot search needs only the text tower: about 175 MB at q4, estimated under 1 GB resident and tens of milliseconds per query on two vCPUs (estimate, Low). `onnxruntime-node` ships glibc builds, so the worker should stay on the existing Debian `bookworm-slim` image, and reported memory growth suggests it should restart itself periodically (Low).

Deferred indexing has a strong precedent: [Ente Photos](https://help.ente.io/photos/features/machine-learning) (High, Primary) runs all ML on the device and syncs encrypted indexes, which Campus Recall already does. [Immich](https://immich.app/docs/features/ml-hardware-acceleration) (Medium, Primary) shows the counterpart: a server answering text queries must run the same model as the indexer. That is why the team's "devices index" decision still needs a server-side text encoder for meaning search in WhatsApp.

Search itself is small. Each student has at most a few thousand chunk vectors, so exact cosine in Node, or pgvector exact search filtered by owner, gives perfect recall in milliseconds; [pgvector's README](https://github.com/pgvector/pgvector) (High, Primary) warns that a shared approximate index filters after the scan and hurts per-tenant recall. The official `postgres:17-alpine` image has no pgvector, and switching the existing data directory to the Debian pgvector image changes collations and forces reindexing ([Crunchy Data](https://www.crunchydata.com/blog/glibc-collations-and-data-corruption); Medium, Established), so brute force in Node is the safer start. PostgreSQL full-text search and `pg_trgm` ship in contrib and give a free keyword fallback over captions, filenames and pdf.js text (Medium). For the job queue, [pg-boss](https://github.com/timgit/pg-boss) (High, Primary) adds backoff and dead-letter queues, but a hand-written `SKIP LOCKED` table of about 50 lines fits the server's few-dependency style.

Linking needs care. Meta says "WhatsApp does not enforce ownership of the phone number past initial registration" and that numbers are recycled ([Meta authentication best practices](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/authentication-templates/authentication-best-practices/); High, Primary); a Princeton study found 171 of 259 sampled recycled US numbers still tied to online accounts ([Krebs on Security](https://krebsonsecurity.com/2021/05/recycle-your-phone-sure-but-maybe-not-your-number/); High, Established; no India data). A BSUID is regenerated when a user changes number, signalled by a `user_changed_number` webhook; whether a recycled number's new owner gets a new BSUID is undocumented. A leaked link, or one opened by the wrong person, links the wrong identity, so the confirmation screen must name the account (analysis).

If server-side extraction is reconsidered later, the estimates are modest: about 1–5 seconds per photo through tesseract.js and 5–15 seconds per one-minute voice note through whisper-tiny on two vCPUs, all within 8 GiB at a concurrency of one, after ffmpeg decodes OGG/Opus (estimate, Low). Keeping the current VM is the cheapest path. (The team has since chosen to run the app's own engine in headless Chromium on the server rather than a Node port; see Proposed architecture.) Full detail: `research/2026-11-10-technical-whatsapp-bot/server-architecture.md`.

### Alternatives and unofficial routes

Unofficial libraries work but cannot be relied on. Baileys, whatsapp-web.js, WPPConnect and Evolution API (in Baileys mode) connect as a linked device, can receive media and are actively maintained, but need a real phone that stays active ([Baileys README](https://github.com/WhiskeySockets/Baileys); High, Primary). WhatsApp says linking an account to an unofficial app breaks its Terms and can bring a temporary or permanent ban ([WhatsApp Help Center](https://faq.whatsapp.com/1217634902127718); High, Primary), and whatsapp-web.js itself says it "shouldn't be considered totally safe". Issue trackers show restrictions and bans through October 2026, some on accounts that sent almost nothing (pattern Medium; each report Low). A malicious Baileys fork on npm, `lotusbail`, with 56,000 downloads, stole messages and sessions in December 2025 ([The Hacker News](https://thehackernews.com/2025/12/fake-whatsapp-api-package-on-npm-steals.html); High, Established). One tempting design deserves an explicit no: linking each student's own WhatsApp to our server to read their "Message yourself" chat would expose every chat on their account and put their personal numbers at ban risk (analysis). Zapier, Make and n8n all use the official Cloud API, so they add cost without removing Meta setup ([n8n WhatsApp trigger](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.whatsapptrigger/); Medium, Primary).

Three no-risk channels complement the bot. Telegram bots are free, link accounts through a one-tap `t.me/<bot>?start=<token>` deep link documented for this purpose, and accept 20 MB downloads, or 2 GB with a self-hosted Bot API server ([Telegram bot features](https://core.telegram.org/bots/features), [Bot API](https://core.telegram.org/bots/api); High, Primary); but WhatsApp, not Telegram, is the "send to self" habit, and no current survey compares the two among Indian students. Web Share Target works for installed PWAs on Android Chrome but not on iOS Safari, where WebKit bug 194593 has been open since 2019 ([MDN compat data](https://github.com/mdn/browser-compat-data/blob/main/manifests/webapp/share_target.json); High, Primary). The earlier UX research had already recommended a share target, because about 94% of Indian mobile web traffic is Android (`research/2026-11-09-product-campus-recall-ux.md`, F7). An iOS Shortcut that posts the shared file to an upload endpoint, and a per-user `save+<token>@…` email address, cover iPhones and any mail app ([Apple Shortcuts guide](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios); Medium, Primary; [Readwise email-in](https://docs.readwise.io/reader/docs/faqs/email-newsletters); High, Primary). Full detail: `research/2026-11-10-technical-whatsapp-bot/alternatives.md`.

### Prior art and adoption

The 2026 platform shock is the key precedent. Meta's October 2025 terms barred general-purpose AI assistants from the Business API from 15 January 2026; ChatGPT, Copilot, Perplexity and Luzia left, and users who had not linked an account lost their WhatsApp history, because bot chats cannot be exported ([TechCrunch](https://techcrunch.com/2025/10/18/whatssapp-changes-its-terms-to-bar-general-purpose-chatbots-from-its-platform/); High, Established). Brazil and the EU forced Meta to reopen access; no Indian relief was found.

Small "second brain on WhatsApp" products exist (Khoj, Voicenotes, Crumbs, Keepi, SaveMyLink, Memorae), but the evidence is their own pages, none publishes credible traction, and none combines multi-format capture, semantic search, return of the original and a local-first app (Medium for existence, Low for traction). The closest Indian precedent is DigiLocker on the MyGov helpdesk, which re-sends the original PDF in chat ([The Quint](https://www.thequint.com/tech-and-auto/digilocker-services-whatsapp-mygov-helpdesk-documents-download-number); High, Established).

The evidence that chat lowers friction is indirect. Zapia reached 3.5 million WhatsApp users against about 500,000 app downloads ([LatamList](https://latamlist.com/zapia-raises-7-25m-seed-extension/); High for the figures), but it was a general assistant in Latin America, so the comparison is confounded. Luzia's CEO called WhatsApp a "secondary channel" used mainly by people with modest phones ([Xataka](https://www.xataka.com/robotica-e-ia/luzia-pierde-whatsapp-acelera-comercio-70-millones-descargas-plan-para-venderte-productos-chat); Medium, Established), which applies less to IITGN students. No public data exists on "Message yourself" usage or on bot-versus-app conversion in India. Our own interviews show the habit directly: one student stars messages and once lost a photo she had shared to a chat she could not remember (`docs/user/U01.md`); the other said "I just share it to my personal no.", still has to scroll to find things there, and worried she "would never know whether I really saved my work" (`docs/user/U02.md`), which argues for an unambiguous "Saved" reply.

Chat retrieval follows four documented patterns: a conversational answer, a re-sent original (DigiLocker), capture in chat with search on the web (SaveMyLink), and a link to a web account (ChatGPT). With 24-character list titles, the fitting design is a hybrid of a short list, the original re-sent on tap, and a link into the app ([Meta list messages](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-list-messages); High, Primary). Full detail: `research/2026-11-10-technical-whatsapp-bot/prior-art.md`.

## Implementation Considerations

### Proposed architecture

A student messages the bot's number. Meta calls `POST /api/v1/whatsapp/webhook` on the existing pilot origin, where Caddy already provides the CA-signed certificate Meta requires. The handler verifies `X-Hub-Signature-256` against the raw body, inserts each message into a `wa_inbound` table keyed by `wamid` with `ON CONFLICT DO NOTHING`, adds a job row in the same transaction, and returns 200. A worker in the same Node process claims jobs with `SELECT … FOR UPDATE SKIP LOCKED`, resolves the media ID, streams the bytes into Blob while hashing them, and publishes a cloud item into the sender's vault through the existing `PilotStore` and `ObjectStore`, so the item appears in the change feed like any other upload. The owner key is a new kind, `wa:<bsuid>`, taken from `messages[].from_user_id`, with the phone number kept only as a nullable display field.

To open the same library in the app, the student sends `OPEN` (or taps a button) and the bot replies with a single-use link valid for ten minutes. The app exchanges the link token for an ordinary session on the `wa:` vault, shows the masked number before continuing, and then behaves exactly as the Google-account Auto-sync does today, including the rule that the local library is never uploaded until the student explicitly includes it (P02).

**Indexing runs on the server for opted-in WhatsApp items (decided 10 November).** A new `engine-host` container runs the built PWA's engine in headless Chromium through Playwright, the same way `pilot/model-e2e/real-model-cross-device.spec.ts` already drives real models against the pilot server. Model files come from `scripts/download-assets.mjs`, which checks every pinned asset's SHA-256 into `.models/`, and are served to the headless page from a local volume exactly as the test routes them. A small dedicated entry page (for example `engine-host.html`, built by Vite and never linked from the app) exposes two functions to Playwright: `indexOriginal(bytes, kind, title)` returning the same `IndexedSegment` list the app stores, and `searchQuery(text, segments)` returning ranked results from the app's own `formatQuery` and `rankSegments`. After the ingester stores an item, it queues an index job; the engine host processes it and the server publishes the bundle through the same checks as `PUT /items/{id}/index` (hash, title digest, `INDEX_VERSION`, 768-d normalised vectors). Because this is the app's code, models and `INDEX_VERSION`, the bundle is interchangeable with a device-made one, and a student who later opens the app searches WhatsApp items through the existing cloud-index merge (P05/P06) with no client change. Running the engine in Chromium rather than porting `src/engine/extract.ts` to Node avoids replacing its DOM canvas, `createImageBitmap` and worker code and avoids any risk of vectors drifting from the app's.

Bot search sends the query to the same engine host, scores it against the owner's stored bundles with the frozen thresholds, and returns at most five results as an interactive list. Tapping a result re-sends the original as a document or image, with a button that opens the app at the page found. An item sent seconds earlier may still be indexing; it is matched by keyword on caption and filename, and the reply says it is still being indexed.

This puts cloud inference on the server for opted-in WhatsApp items only. The root SPEC prose ("no cloud inference") and pilot P06 describe the app and stay true for it; the bot needs its own statements and a privacy notice that says plainly that its files and queries are processed on our server. No root test changes.

### Format and limit mismatches to handle

WhatsApp and the app accept different formats, and the bot must handle each mismatch explicitly. WhatsApp caps inbound images at 5 MB and recompresses photos sent the normal way, so the stored "original" is WhatsApp's copy; students who want the full-quality file should send it as a document (common WhatsApp behaviour, to be checked during the demo). WhatsApp allows 100 MB documents, but the app accepts PDFs only up to 20 MB and 50 pages, so the bot must refuse larger files with a clear reason. Voice notes arrive as OGG/Opus, which the app does not accept (MP3, WAV and M4A only), so the demo should either decline voice notes politely or transcode them with ffmpeg and label the stored file as converted. DOCX, PPTX and XLSX are outside the app's supported kinds and should be declined. A plain-text message becomes a note; a message that is only a URL can be stored as a note with `sourceUrl`, because the app's webpage kind expects a text snapshot.

### Security and compliance checklist

- Verify every webhook signature with the app secret; keep the app secret and system-user token as mounted secret files like the existing Google secret.
- Never store anything before the student replies `AGREE` to a short notice covering what is stored, that Meta decrypts and keeps messages up to 30 days, where the data lives, and how to delete it; ask for an 18+ confirmation.
- Support `DELETE ALL` (reusing the existing vault removal and epoch increment), `STOP`, `HELP` (team email for grievances and human escalation) and `PRIVACY` (link to a bot-specific privacy notice).
- Keep the existing "app queries never leave the device" promise for the app, and describe the bot as a separate opt-in channel whose queries pass through Meta and our server.
- Treat a `user_changed_number` webhook as a reason to suspend the link until the student re-confirms in the app.
- Exempt the webhook route from the per-address rate limiter (all of Meta's calls would otherwise share a few per-address buckets) but keep a per-sender limit.
- Never train or fine-tune anything on WhatsApp content (Meta Terms 4.7).

## Key Findings

**1. It is possible on the official route, with no company and no cost at demo scale.** According to Meta's Get Started guide, personal Facebook accounts, a developer app and a self-created business portfolio are enough to get a test number, and test resources need no payment method ([Meta Get Started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started.md); Medium, Primary). The test number reaches only about five allow-listed phones (Low–Medium), which suits a reviewer demo but not a cohort. A real launch needs a fresh SIM, because a number already on WhatsApp cannot be registered ([Meta phone numbers](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers); High, Primary).

**2. Saving is the easy half, because this codebase already has the vault.** The pilot server's upload path, quota, change feed, deletion and backups (`docs/pilot/protocol.md`) are what a WhatsApp ingester needs. The new work is the webhook, a job queue, an identity type for WhatsApp senders, and consent and command handling. Meta's media URLs expire after five minutes, so the copy into Azure must happen at once ([Meta media reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media); High, Primary).

**3. Searching in WhatsApp is the hard half, and it changes the privacy story.** With indexing left on devices, the server still has to embed the query with the identical pinned model, or results cannot be compared ([model card](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX); Medium, Primary; [Immich](https://immich.app/docs/features/ml-hardware-acceleration); Medium, Primary). Every bot query and file passes decrypted through Meta, which keeps it up to 30 days, and through our server ([Meta Cloud API privacy](https://developers.facebook.com/documentation/business-messaging/whatsapp/data-privacy-and-security); High, Primary). This suggests the bot must be presented as a separate opt-in channel, leaving the app's "no query text leaves the device" promise unchanged.

**4. Server indexing closes the gap for students who never open the app.** If devices did all indexing, an item sent by WhatsApp would not be searchable by meaning until the student opened the app once on a device with the 445 MB models (analysis from the server-architecture note). The team therefore decided on 10 November that the server indexes opted-in WhatsApp items, using the app's own engine in headless Chromium so the bundles match device-made ones. The cost is server memory and CPU on the 2-vCPU VM, which must be measured, and cloud inference for opted-in items.

**5. The free lunch ended on 1 October 2026, and the platform can change its mind.** Meta now charges about ₹0.115 plus GST per reply after 1,000 free replies a month per number ([Meta pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing); High, Primary). Meta's January 2026 ban removed ChatGPT and Copilot from WhatsApp, and users without a linked account lost their history ([TechCrunch](https://techcrunch.com/2025/10/18/whatssapp-changes-its-terms-to-bar-general-purpose-chatbots-from-its-platform/); High, Established). A narrow retrieval-only bot is probably "ancillary" under Section 4.7, but Meta has sole discretion (analysis, Low–Medium). The pattern across sources indicates that the app and the Azure vault, not the chat, must stay the system of record.

## Pros and Cons

**Pros**

- It meets students where the habit already is. Both interviewees already rely on WhatsApp to keep and find things: one stars messages, the other forwards things to her own number (`docs/user/U01.md`, `docs/user/U02.md`). Forwarding to a pinned bot takes the same taps as forwarding to yourself (analysis).
- There is no install and no 445 MB download before the first save.
- It reuses the pilot's vault, upload checks, quota, change feed, deletion and backups (`docs/pilot/protocol.md`).
- WhatsApp supplies a `sha256` for each file, so the stored copy can be checked byte for byte ([Meta webhook reference](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/reference/messages/document); Medium, Primary).
- It costs nothing at demo scale, and roughly ₹0 to ₹750 a month for 20 to 100 students (pricing-note estimate on Meta's High-confidence rate card).
- There is a credible Indian precedent for retrieving originals in chat: DigiLocker on the MyGov helpdesk (High, Established).

**Cons**

- It breaks the local-first promise for bot users. Meta decrypts the chats, the WhatsApp app labels them as not end-to-end encrypted, and our server sees queries (High, Primary).
- It depends on the platform. Meta's policy discretion, pricing changes, number bans and the INR billing deadline of 31 December 2026 are all outside the team's control (High–Medium, Primary).
- The test number reaches only about five people (Low–Medium). A real launch needs a new SIM and Meta Business Manager setup, and without business verification students may see a raw number rather than "Campus Recall" (Medium).
- Formats do not line up: photos are recompressed, voice notes arrive as OGG, documents can be up to 100 MB while the app takes 20 MB, and Office files are not supported.
- Server indexing adds load to the 2-vCPU, 8 GiB VM (Chromium plus models; not yet measured) and means opted-in items are processed in the cloud.
- WhatsApp-number vaults sit outside the IITGN-only eligibility check, which widens who can use the service and brings DPDP duties (in force around May 2027) closer.
- It adds operational burden: webhook uptime, a token and app secret to rotate, and a hosted pilot that currently ends on 6 December 2026.

## Strategic Recommendations

1. **Build the demo on the official Cloud API test number, not an unofficial library.** It is free, needs no company and carries no ban risk. Baileys-style libraries are against WhatsApp's Terms, and bans were still being reported in October 2026. Evidence: notes/cloud-api-mechanics.md, notes/alternatives.md.
2. **Prove the headless engine host first, then build around it.** It is the one piece with real uncertainty (memory on the VM, Chromium in the deploy image). A day-one spike that indexes a fixture PDF and photo and gets the bundle accepted settles it. Evidence: notes/server-architecture.md, `pilot/model-e2e/`.
3. **Ship saving before bot search.** Saving reuses existing server code and answers the reviewers' main point on its own; keep a keyword fallback on captions and filenames for items still indexing. Evidence: notes/server-architecture.md.
4. **Key identity on the business-scoped user ID and send the app link from the bot.** Meta says to identify users by `from_user_id`. The magic-link confirmation screen must name the account to avoid linking the wrong person. Evidence: notes/cloud-api-mechanics.md, notes/server-architecture.md.
5. **Also add the Android share target.** It is cheap, carries no risk, keeps processing on the device, and the earlier UX research had already recommended it. Evidence: notes/alternatives.md, research/2026-11-09-product-campus-recall-ux.md.

After each stored item it indexes and publishes the bundle. A storage test runs a fixture through ingest → index → bundle and checks W7.

**Phase 3 — Search in WhatsApp and open in the app (19–22 Nov).** Route text messages that are not commands to `searchQuery` over the sender's bundles; reply with a list of up to five, re-send the chosen original, and add an open-in-app button. If the spike shows the VM cannot hold Chromium and the models alongside the API, the fallback for the demo is to run the engine host on a team laptop that pulls index jobs from the pilot API over HTTPS, and to report that limitation plainly.

## Risks and Uncertainties

- **Data gaps.** The test number's five-recipient cap appears only on Meta's legacy page and in vendor docs. There are no measured CPU numbers for EmbeddingGemma 2 in Node on 2 vCPUs, and no confirmation that the native backend works without the q4 Gather patch. It is undocumented whether forwarded documents carry `context.forwarded`, how albums arrive (community reports say one webhook per item), whether a recycled number's new owner gets a new BSUID, and what the exact in-chat encryption label for a Cloud API chat says. No public data compares WhatsApp-bot and app-install conversion or shows "Message yourself" usage. No IITGN policy on student apps, and no CCI action on Meta's AI-provider clause, was found.
- **Low-confidence claims.** The Azure cost figures come from one Microsoft API. The latency and memory estimates are inferred from phone benchmarks. The reading that a retrieval bot is "ancillary" under Meta's Terms is our interpretation, not legal advice; so is the view that the team would be a DPDP Data Fiduciary. The ban-pattern evidence for unofficial libraries rests on individual issue reports.
- **Conflicts.** Webhook retry windows are given as 7 days (WhatsApp docs), 36 hours (Graph docs) or 8 hours (a community post); the design assumes 7 days. The inbound media `url` field is dated 16 October 2025 (changelog) or 12 November 2025 onward (reference pages); the code handles both. India's service rate is ₹0.115 on Meta's list against ₹0.127 to ₹0.145 from resellers; the pricing note traced the difference to reseller markup and GST and uses Meta's rate. Meta's "WhatsApp cannot access any message content" snippet conflicts with the fetched page's "decrypts the message"; the report follows the fetched page. A vendor's claim of mandatory AI disclosure is not in the primary policy text. Commentators date the DPDP 18-month mark as 12, 13 or 14 May 2027.
- **Things to watch.** Meta's AI-provider policy and any CCI action. The 31 December 2026 INR billing deadline and the next possible rate change on 1 January 2027. Azure for Students credit burn. The 6 December pilot end. Memory headroom for Chromium plus models on the 2-vCPU, 8 GiB VM.
